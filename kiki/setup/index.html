kiki Setup

full setup guide

kiki is a local-first encrypted vault for iPhone. Files are encrypted on-device (AES-256-GCM). A hub you run stores ciphertext. Optional remote sessions are a temporary pipe to the same hub (not a second vault). Optional shared tags filter what a guest device syncs.

Use TestFlight build 1.0.0 (13)+ for durable LAN hub URLs, fail-closed import, remote session cleanup, and fixed multi-device wraps. Older builds can poison the vault with a phone-private key or broken remote uploads.

Arcane Data does not host your files. The hub and keys stay under your control.

2. Install the iPhone app

1

Install TestFlight

From the App Store, install Apple’s TestFlight app if you don’t have it.

2

Accept the kiki beta invite

Open the TestFlight link from the person running the beta (or the button on arcanedata.us/kiki). Install kiki and update to the latest build.

3

Open kiki and unlock

Allow Face ID / passcode when asked. Allow Local Network when prompted (needed for hub discovery and LAN join).

3. Hub on your home network (LAN)

The hub stores encrypted blobs under ~/.kiki-hub and advertises itself on the LAN (port 8787).

1

On your Mac, open Terminal

Spotlight → Terminal.

2

Install & start the hub

bash <(curl -fsSL https://arcanedata.us/kiki/hub/install.sh)

Installer prints something like http://192.168.x.x:8787. Keep that address — that is your durable hub URL.

3

Connect the phone

Same Wi‑Fi as the Mac. kiki should auto-discover the hub. If not: Settings → hub url → paste http://YOUR_LAN_IP:8787 (never the phone’s own localhost) → test connection → sync now.

4

Verify

Home status should show connected. Import a test file → it should sync. Import from Files / Desktop is supported on build 13+ (kiki copies the file before encrypting).

NAS / Linux:

bash <(curl -fsSL https://arcanedata.us/kiki/hub/nas-install.sh)
Dev / from source: clone kiki-personal-vault, then:
cd hub && go build -o /tmp/kiki-hub ./cmd/hub && /tmp/kiki-hub -addr 0.0.0.0:8787
Stop a running hub with:
kill $(lsof -t -iTCP:8787 -sTCP:LISTEN)
Restart after hub updates so it reloads ~/.kiki-hub.

4. Hub URL rules (read this)

UseDon’t
http://192.168.x.x:8787 (your Mac/NAS LAN IP) http://127.0.0.1:8787 on a physical iPhone — that is the phone, not the Mac
Empty hub URL only for single-device offline mode Leave a saved loopback URL after a remote session ends (build 13 clears/restores LAN automatically)
Settings → test connection before big imports Import while hub is unreachable with a hub URL configured (import will abort on purpose)
If hub URL is set but the hub is offline, kiki aborts import so it does not seal files with a private phone key. That fail-closed behavior is intentional.

5. Second device on the same Wi‑Fi

1

Install kiki (same TestFlight build 13+)

2

Join the same hub

Same Wi‑Fi → auto-discover, or enter the Mac LAN hub URL manually. Tap test connection.

3

Sync first (before importing)

Settings → sync now. The phone adopts the hub’s account vault key (AVK). If anything looks incompatible: Recover from hub, then sync again.

Do this before importing lots of new files on a fresh install. A phone that mints its own key and uploads can make hub files unreadable for everyone else.

6. Vault key best practices (one identity, every path)

kiki follows the usual envelope-encryption model used by serious multi-device vaults: one account vault key (AVK) on the hub, per-file keys wrapped under that AVK, ciphertext on the hub only. LAN and remote are transport only — same blobs, same AVK.

Design rules (what “correct” means)

PrincipleWhat you do in the app
One vault identity The hub holds a single AVK envelope. Every phone that syncs adopts that key. The hub refuses a second device overwriting it.
Transport ≠ crypto Home Wi‑Fi and a remote session only change how you reach the hub. Encryption rules never change with the path.
Fail closed If a hub URL is set but the hub (or AVK) can’t be loaded, import aborts instead of sealing with a private phone key.
Ephemeral remote Remote join uses a short-lived ticket and a temporary loopback proxy. Ending the session restores your durable LAN hub URL. No secrets are baked into the app binary.
Universal accessibility After any healthy upload (LAN or remote), another device with the hub AVK must open the file with plain sync — no path-specific recovery ritual.

Healthy multi-device flow

1

First phone (or the one that already works)

Durable hub URL = Mac/NAS LAN IP → test connection → sync. Import files only after the hub is reachable so wraps use the hub AVK.

2

Every new phone

Same hub URL → sync (or Recover from hub if anything looks wrong) before importing new files. That pulls the shared AVK.

3

Away from home

Join remote session → sync/import as usual → end session. You should still open those files later on LAN with the same hub.

Do / don’t

DoDon’t
Use build 13+ (hub AVK before encrypt; durable LAN URL; wrap header transport) Assume remote uses different encryption than LAN
Sync/recover on a new device before bulk import Import/upload from a phone full of “incompatible” files
Keep one durable hub URL (http://LAN_IP:8787) Save 127.0.0.1 as the permanent hub on a physical iPhone
Restart the hub process after hub updates so it reloads data Leave a broken device uploading — it can confuse the library even though the hub blocks AVK overwrite
Recover from hub → sync; re-import originals only if still dead Delete + suppress without trying recover first
“Incompatible” means this device can’t unwrap the file key (wrong/missing AVK, or a historically corrupted wrap). It is not “the remote path uses different crypto.” Build 13+ and a restarted hub fix the known wrap-transport bug; remaining failures after Recover usually mean the original seal key is gone — re-add from the source file on a healthy device.

If only the newest file opens, older hub wraps were likely sealed under a lost device key — re-add those files from the original copies on a device that still opens them.

7. Shared files (MVP)

This is a sync filter, not a separate crypto compartment. Same vault key; you choose what a “shared-only” device shows and pulls.

1

On the host phone

Files tab → on a tile tap the people icon to tag shared (chip appears). Leave personal files untagged.

2

Sync with “sync shared only” OFF on the host

So tags upload to the hub with the blobs.

3

On the guest phone

Settings → enable sync shared only → sync. Guest library filters to shared-tagged files.

Honest limit: if a guest already did a full sync earlier, personal files may already be on that device. Shared-only does not erase history or use a separate encryption key yet.

8. Remote access (away from home)

Goal: phone on cellular/other Wi‑Fi reaches your home vault without opening the hub to the public internet. The hub agent dials out to a short-lived rendezvous (Rn); you share a ticket/QR. Remote is an ephemeral overlay: same AVK, same blobs; when the session ends, the phone restores your LAN hub URL.

A. What runs on the home Mac

  1. Hub on LAN (port 8787) — stores blobs; not published as a public URL.
  2. Rendezvous on port 8788 — session broker + relay.
  3. Public HTTPS front for Rn only (MVP: ngrok) so phones can join with TLS.

B. From source (developer MVP)

Terminal 1 — rendezvous (after you have an HTTPS public base):

cd /path/to/kiki-personal-vault/hub go build -o /tmp/kiki-rn ./cmd/rn go build -o /tmp/kiki-hub ./cmd/hub # Example: ngrok http 8788 → copy the https://….ngrok-free.app URL as PUB export PUB="https://YOUR-NGROK-SUBDOMAIN.ngrok-free.app" /tmp/kiki-rn -addr 127.0.0.1:8788 \ -local-base http://127.0.0.1:8788 \ -public-base "$PUB" \ -token dev-agent-token

Terminal 2 — hub (agent talks to local Rn; listen on LAN so home phones still work):

export KIKI_RN_URL=http://127.0.0.1:8788 export KIKI_RN_TOKEN=dev-agent-token export KIKI_PUBLIC_HUB_URL="$PUB" /tmp/kiki-hub -addr 0.0.0.0:8787

Terminal 3 — public tunnel to Rn (not the hub):

ngrok update # need a current agent ngrok http 8788
Free ngrok URLs change when the tunnel restarts. Paid/stable domains or a self-hosted Rn are better for real use. Restart Rn with the new -public-base whenever the tunnel URL changes.

C. Start a session & join

1

Host: start remote session

In kiki (on home Wi‑Fi, durable hub URL set to Mac LAN IP): Settings → remote session → start + show qr.

2

Share the claim link / QR

QR encodes an HTTPS claim URL on the public Rn, e.g. https://….ngrok-free.app/claim?t=eorp1:… — not http://127.0.0.1.

3

Guest: join

Scan with Camera → Open in kiki, or kiki → Settings → scan qr / paste ticket → join. Status becomes an ephemeral loopback proxy (temporary only). Then sync or import. Hub field stays locked while remote is active; durable LAN URL is preserved underneath.

4

End when done

Guest: end remote session (LAN hub URL restores). Host: stop remote session. Tickets expire (default ~15 minutes). Do not save the temporary proxy as your permanent hub.

D. Security notes (remote)

  • Hub port stays private; only Rn is public.
  • Ticket is a short-lived capability — treat QR like a temporary password.
  • Rn access logs show join attempts.
  • Vault plaintext never goes to Rn unencrypted; same AVK as LAN.
  • Build 13+ sends file-key wraps outside the URL query string so remote uploads stay readable on every device.
